# Manual Testing Guide for RabbitMQ Message Listener

This guide outlines the steps to manually test the new RabbitMQ message listener functionality (`TaskListenerService`) in the `backend-worker` module.

## Prerequisites

1.  **Running RabbitMQ Instance:** Ensure you have a RabbitMQ server running and accessible, with the exchanges and queues defined in `AmqpConfig.kt` created.
2.  **RabbitMQ Management UI:** Access to the RabbitMQ Management UI (typically at `http://localhost:15672/`) is highly recommended for sending messages and observing queues. Alternatively, `rabbitmqadmin` CLI or other tools can be used.
3.  **Worker Application Running:** The `backend-worker` application must be running with the new `TaskListenerService` active.
4.  **Log Access:** Ability to view the logs generated by the `backend-worker` application.

## Testing Steps

### 1. Sending a Test Message to `compileQueue`

*   **Method:** Using RabbitMQ Management UI
    1.  Navigate to the RabbitMQ Management UI.
    2.  Go to the "Queues" tab.
    3.  Find and click on the queue name configured for `amqp.queue.compile` (e.g., `oj.compile.tasks` by default, check `application.yml` or `AmqpConfig.kt` for actual names if customized).
    4.  In the queue's page, find the "Publish message" section.
    5.  **Payload:** Enter a sample JSON or text payload. For basic testing, any string like `{"sourceCode": "printf('hello');"}` is fine. The `TaskProcessor` might expect a specific format for full processing.
    6.  **Properties:**
        *   Set `correlation_id` to a unique value (e.g., `test-compile-job-001`). This helps in tracking the message in logs.
        *   Ensure `content_type` is `application/json` if sending JSON.
    7.  Click "Publish message".

### 2. Sending a Test Message to `executeQueue`

*   **Method:** Using RabbitMQ Management UI (similar to `compileQueue`)
    1.  Navigate to the "Queues" tab in RabbitMQ Management UI.
    2.  Find and click on the queue name configured for `amqp.queue.execute` (e.g., `oj.execute.tasks` by default).
    3.  In the "Publish message" section:
    4.  **Payload:** Enter a sample payload, e.g., `{"compiledArtifactPath": "/path/to/artifact"}`.
    5.  **Properties:**
        *   Set `correlation_id` to a unique value (e.g., `test-execute-job-002`).
        *   Ensure `content_type` is `application/json` if sending JSON.
    6.  Click "Publish message".

### 3. Observing Logs for Message Reception by `TaskListenerService`

*   Check the `backend-worker` application logs.
*   Look for log entries similar to:
    ```
    INFO --- [cTaskExecutor-1] o.r.s.w.i.a.TaskListenerService    : Received compile task via listener for jobId: test-compile-job-001 (deliveryTag: <some_number>) from queue: <compile_queue_name>
    ```
    or
    ```
    INFO --- [cTaskExecutor-1] o.r.s.w.i.a.TaskListenerService    : Received execute task via listener for jobId: test-execute-job-002 (deliveryTag: <some_number>) from queue: <execute_queue_name>
    ```
*   The `jobId` should match the `correlation_id` you set. The `deliveryTag` is assigned by RabbitMQ. The queue name should match the target queue.

### 4. Observing `TaskProcessor` Invocation

*   After the message reception log, look for logs from the `TaskProcessor` (e.g., `DefaultTaskProcessor`).
*   These logs would typically indicate the start and end of message processing by the `TaskProcessor`, for example:
    ```
    INFO --- [cTaskExecutor-1] o.r.s.w.i.a.DefaultTaskProcessor : Processing message with correlationId: test-compile-job-001 from queue: <compile_queue_name>
    INFO --- [cTaskExecutor-1] o.r.s.w.i.a.TaskListenerService    : Successfully processed compile task for jobId: test-compile-job-001
    ```
*   The exact log messages depend on the implementation of `TaskProcessor`.

### 5. Testing Error Handling and Dead Letter Queue (DLQ)

*   **Inducing an Error:**
    *   To test error handling, send a message that is known to cause an exception within `TaskProcessor`. This might involve:
        *   Sending a malformed JSON payload if the processor expects JSON.
        *   Sending a payload that leads to a specific business logic error handled by the processor.
        *   If the `TaskProcessor` interacts with external services (like Minio), you could temporarily make that service unavailable.
    *   For example, send a message with an invalid structure to `compileQueue`.

*   **Observing Retry Attempts (if visible in logs):**
    *   The current `TaskListenerService` logs errors *after* retries are exhausted by the container's `RetryInterceptor`.
    *   To observe retries more directly, you might need to add temporary debug logging within the `processMessage` method of `TaskProcessor` or rely on RabbitMQ Management UI showing increased "deliver_get" rates for the queue if messages are redelivered quickly.
    *   The `RetryInterceptor` is configured with an initial interval, multiplier, and max attempts (e.g., 1s, 2.0, 3 attempts). You should see a delay between the logged processing attempts if the error is persistent.

*   **Observing Message in DLQ:**
    1.  After the configured number of retry attempts (default 3), the message should be rejected and sent to the Dead Letter Queue.
    2.  In the `backend-worker` logs, you should see an error log from `TaskListenerService` like:
        ```
        ERROR --- [cTaskExecutor-1] o.r.s.w.i.a.TaskListenerService    : Error processing compile task for jobId: <error_job_id> after retries from queue: <compile_queue_name>. Error: <exception_message>
        ```
    3.  Go to the RabbitMQ Management UI -> "Queues" tab.
    4.  Find the dead letter queue corresponding to the original queue:
        *   For `compileQueue`, this is `amqp.queue.compile-dlq` (e.g., `oj.compile.tasks.dlq`).
        *   For `executeQueue`, this is `amqp.queue.execute-dlq` (e.g., `oj.execute.tasks.dlq`).
    5.  The DLQ should have one message (or an increased message count). You can inspect the message in the DLQ to confirm it's the one that failed.

### 6. Checking `prefetchCount` Effect

*   **Concept:** `prefetchCount` (e.g., set to 10 in `application.yml`) means the worker will only receive and process up to 10 messages concurrently from a queue, even if more messages are available. This prevents the worker from being overwhelmed.
*   **Testing:**
    1.  Ensure the `TaskProcessor` has a noticeable processing delay for each message (e.g., add `Thread.sleep(5000)` in `processMessage` for testing purposes).
    2.  Send a batch of messages (e.g., 20-30 messages) to either `compileQueue` or `executeQueue` in quick succession using the RabbitMQ Management UI or a script.
    3.  **Observe Worker Logs:** You should see logs indicating that roughly `prefetchCount` (e.g., 10) messages are being processed concurrently. Subsequent messages will only start processing as earlier ones complete.
    4.  **Observe RabbitMQ Management UI:**
        *   Go to the queue's page.
        *   You should see messages moving from "Ready" to "Unacked". The number of "Unacked" messages should ideally not exceed the `prefetchCount` significantly for a single worker instance. If it does, it might indicate messages are being delivered but not yet acknowledged by the listener, or the prefetch setting isn't taking effect as expected.
        *   If you have multiple worker instances, the total unacked messages across all instances would relate to `prefetchCount * number_of_instances`.

## Expected Outcomes

*   Messages sent to `compileQueue` and `executeQueue` are logged as received by `TaskListenerService`.
*   `TaskProcessor` logs indicate it's processing these messages.
*   Error-inducing messages result in error logs and eventually land in the correct DLQ after retry attempts.
*   The worker adheres to the `prefetchCount` when handling a large volume of messages.
