# **贪吃蛇算法竞技平台前端系统交接文档**

## **系统概览**

本平台是一款支持多人对战“贪吃蛇”游戏的算法竞赛系统，其中前端负责完整的游戏状态维护和展示，后端负责代码编译和运行。前后端采用分布式架构解耦：**前端使用 Vue3 + TypeScript 技术栈开发**，运行在浏览器中，承担游戏逻辑模拟、用户交互和画面渲染等工作；**后端基于 Spring Boot 构建**，通过沙箱环境编译/执行选手算法，并提供 REST API 与 SSE（Server-Sent Events）接口供前端调用[GitHub](https://github.com/SageSeekerSociety/snake/blob/a9d1ff2eabff0f1409829c2e976fdc1b69594abe/docs/codebase.md#L5-L8)。这种设计使得**前端每个游戏回合收集环境状态并发送给后端**，后端仅返回算法决策结果（如移动方向），**不直接介入游戏规则判断**[GitHub](https://github.com/SageSeekerSociety/snake/blob/a9d1ff2eabff0f1409829c2e976fdc1b69594abe/docs/codebase.md#L5-L8)。平台功能包括：用户登录注册（集成了 Cheese-Auth 模块和学校 OAuth 服务），代码提交与编译，实时对战模拟，赛事排名和回放等。前端通过 JWT Token 实现身份认证与后端接口安全通信，所有服务通过 Nginx 反向代理作为统一入口部署。

前端的整体定位是**竞赛选手客户端和比赛可视化工具**。它提供直观的用户界面：包括代码上传编译界面、对战房间创建与游戏观战界面，以及赛事排行榜和比赛规则说明页面等。通过现代浏览器的能力，前端实现了帧动画级的画面渲染、实时消息推送以及本地数据存储（例如游戏录像）的功能，确保选手能够方便地调试算法、观看比赛过程，并支持运维人员水平扩展系统（增加后端节点处理更多并发）而无需修改前端逻辑。

## **代码结构与模块说明**

前端项目采用**模块化结构**，按照功能划分目录，代码清晰易于维护。主要的代码目录及模块如下：

-   **页面视图 (`src/views/`)**：包含应用的页面级组件，每个页面对应路由。例如：
    
    -   `Home.vue`：主页/概览界面（登录后默认页）。
        
    -   `Login.vue` 和 `Register.vue`：登录与注册界面，通过 OAuth 或用户名密码认证用户。
        
    -   `Game.vue`：对战游戏界面，核心模块之一，实现玩家选择参赛AI和实时对战显示。
        
    -   `SubmitCode.vue`：代码提交页面，提供源码上传并调用编译服务的接口。
        
    -   `GameRecordings.vue`：游戏录像列表页面，可查看历史对局录像。
        
    -   `GameReplay.vue`：游戏回放页面，加载并播放指定录像数据。
        
    -   `Tournament.vue` / `TournamentDisplay.vue`：赛事模式界面，用于创建锦标赛和展示赛程/比分等。[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/router/index.ts#L4-L13)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/router/index.ts#L53-L61)
        
-   **通用组件 (`src/components/`)**：可复用的UI组件或布局模块，辅佐页面视图。包括：
    
    -   **游戏UI面板**：如 `GameUILeft.vue` 和 `GameUIRight.vue`，分别为游戏界面的左侧信息面板和右侧计分板组件。左侧面板显示当前对局种子、剩余时间计时器以及事件通知列表[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUILeft.vue#L4-L12)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUILeft.vue#L22-L31)；右侧面板实时显示每条蛇的得分、状态（死亡或存活）、护盾冷却和钥匙持有情况等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUIRight.vue#L4-L13)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUIRight.vue#L22-L30)。
        
    -   **结果弹窗**：如 `GameRankings.vue`，在对局结束时弹出，展示最终排名、得分，并提供保存录像等功能（通过事件通知父组件）。
        
    -   **比赛组件**：如 `tournament/StageView.vue` 等，用于锦标赛阶段展示，每个组件渲染赛事不同阶段的结果或赛程。
        
    -   **其他控件**：如按钮、输入框等像素风格UI控件，在各页面中复用（例如带像素边框的按钮样式`pixel-button`等，在样式表中定义）。
        
-   **路由配置 (`src/router/`)**：前端路由采用 Vue Router。`index.ts` 定义了各页面路径与组件映射，并配置路由守卫实现认证检查。在路由守卫中，若目标路由需要登录而当前未登录用户没有Token，则自动跳转到登录页面；反之已登录用户访问登录/注册页会被重定向到首页[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/router/index.ts#L89-L98)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/router/index.ts#L100-L109)。路由配置方便拓展新的页面或功能模块。
    
-   **实体与游戏逻辑模块**：
    
    -   **游戏实体 (`src/entities/`)**：定义游戏中的核心对象类，如 `Snake.ts`（蛇）、`Food.ts`（食物）、`Obstacle.ts`（障碍物）、`TreasureChest.ts`（宝箱）、`Key.ts`（钥匙）等。每个实体类封装了自身状态和行为，例如蛇对象包含身体坐标列表、当前方向、长度、得分、护盾状态等属性，并提供更新方向、移动、死亡判定等方法[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L30-L39)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L110-L118)。这些实体类被游戏管理器使用，用于构建和更新游戏状态。
        
    -   **游戏管理器 (`src/managers/`)**：包括一系列管理游戏运行各方面的类：
        
        -   `GameManager.ts`：**游戏总管理器**，协调整个对局流程。它持有主要子系统实例（计时器、实体管理、碰撞检测、输入处理、决策协调等），负责初始化游戏、启动/停止回合循环，以及调度每个游戏Tick的逻辑[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L30-L38)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L40-L48)。`GameManager` 内部封装了**游戏主循环**（由 `GameClock` 定时触发）和状态更新流程，详细见后文“核心流程”部分。
            
        -   `EntityManager.ts`：**实体管理器**，维护所有游戏实体的集合及其空间分布。内部使用**空间哈希网格**加速碰撞检测，将实体位置映射到格子索引便于快速查询邻近物体[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/CanvasManager.ts#L22-L28)。该管理器提供添加/移除实体的方法、获取当前全部或存活蛇列表等接口[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L140-L148)。它还实现了诸如清理无效实体、更新动画状态、处理蛇死亡收尾等逻辑，并通过事件总线监听来自其他系统的事件（如安全区缩小时清除越界食物[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L73-L81)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L89-L97)）。
            
        -   `CanvasManager.ts`：**画布渲染管理器**，负责将当前游戏状态绘制到HTML5 Canvas。构造时初始化多个离屏画布层（背景层、障碍物层等）叠加在主画布上[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/CanvasManager.ts#L20-L28)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/CanvasManager.ts#L41-L49)。它组合了一系列**渲染器**（SnakeRenderer、FoodRenderer、ObstacleRenderer等）分别绘制不同类型实体，实现分层绘制和像素风格渲染效果（禁用抗锯齿、绘制像素网格背景等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/CanvasManager.ts#L73-L81)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/CanvasManager.ts#L88-L96)）。`CanvasManager.render()` 方法每帧被调用，遍历所有需绘制实体并调用对应渲染器，将贪吃蛇、食物、宝箱和钥匙等元素绘制在画布上，同时渲染涡流场和安全区范围[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L827-L837)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L845-L853)。它还提供方法预绘制静态障碍以提高性能[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L224-L232)。
            
        -   其他管理器：如 `GameClock.ts`（游戏时钟，维护总Tick数和定时调用更新函数）、`CollisionDetector.ts`（碰撞检测器，用于检测蛇与蛇、蛇与食物/障碍的碰撞并返回碰撞结果）、`InputHandler.ts`（输入管理，处理玩家通过键盘触发的方向或护盾指令），`VortexFieldManager.ts`（管理时局中的随机涡流场效果），`SafeZoneManager.ts`（管理安全区缩圈机制），`TreasureSystem.ts`（管理宝箱/钥匙逻辑，比如定时生成宝箱、处理钥匙掉落/拾取）等。这些模块各司其职，通过事件或直接方法调用与 `GameManager` 协同运作。
            
    -   **工厂与策略 (`src/factories/` 和 `src/strategies/`)**：
        
        -   `EntityFactory.ts` 实现**实体工厂**，根据给定参数创建初始蛇、障碍物、食物等实体对象。例如 `createInitialSnakes` 方法根据选择的玩家列表生成对应数量的 Snake 实例，将每个蛇的决策策略设定为玩家控制或AI控制[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L191-L199)。工厂使创建不同模式的对局变得灵活（可以很方便地更换初始地图布局或蛇的策略）。
            
        -   策略模式用于决定蛇每回合的动作。`src/strategies/` 下定义了多种 **SnakeDecisionStrategy** 策略类[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L23-L27)并实现其 `makeDecision` 接口：
            
            -   `PlayerDecisionStrategy`：玩家控制策略，用于可操控的蛇，只记录最近的方向或护盾按键，在每个Tick应用到蛇上[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L14-L23)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L44-L52)。
                
            -   `AIDecisionStrategy`：内置简单AI策略，可注入一个算法函数让蛇根据当前状态采取行动[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L84-L92)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L97-L105)。例如项目提供的 `ChasingDecisionStrategy` 等示例AI，实现基本追逐目标或随机走动逻辑。
                
            -   `APIDecisionStrategy`：**远程API策略**，也是平台核心策略，负责将蛇的决策委托给后端运行的选手代码。它持有**决策请求协调器**实例和玩家身份ID，在每个Tick组装当前游戏状态的输入数据并通过协调器发送批量执行请求[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L214-L224)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L226-L235)。随后异步等待后端返回结果，再解析方向或动作，将结果应用到蛇实例[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L239-L248)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L261-L269)。若执行成功则设置蛇的新方向/开启护盾，若失败或超时则通过事件触发将该蛇判定为死亡[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L270-L275)（具体见下文“状态管理机制”）。策略模式的存在使得**支持多种蛇控制方式**成为可能，新增加一种策略仅需实现接口并在创建蛇时指定即可，符合开闭原则。
                
    -   **事件总线 (`src/core/EventBus.ts`)**：封装发布-订阅模式的全局事件总线，实现模块解耦。游戏过程中不同组件和系统通过事件总线通信：例如 `GameManager` 在游戏初始化时通过事件总线发送 `UI_UPDATE_SCOREBOARD` 和 `UI_UPDATE_TIMER` 事件来通知UI刷新计分板和倒计时[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L230-L238)；当某条蛇死亡完成动画时，Snake类会触发 `SNAKE_DEATH_ANIMATION_COMPLETE` 事件，EntityManager 监听该事件以执行清理操作[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L61-L69)。事件总线为**UI层与逻辑层之间架起桥梁**：UI组件（如计分板和通知面板）在挂载时订阅相关事件，在游戏运行时自动更新显示[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUILeft.vue#L116-L124)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUIRight.vue#L180-L188)。例如，计分板组件 `GameUIRight.vue` 监听 `UI_UPDATE_SCOREBOARD` 事件以获取新的蛇列表并重排显示名次[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUIRight.vue#L180-L188)；左侧通知面板监听 `UI_NOTIFICATION` 事件将文本消息加入列表显示[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUILeft.vue#L74-L82)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUILeft.vue#L116-L124)。这种基于发布订阅的机制提高了模块间协作的松耦合性，方便以后扩展新的事件类型或UI元素。
        
-   **服务与工具模块**:
    
    -   **API 客户端 (`src/services/`)**：封装与后端交互的 HTTP 客户端和业务服务方法：
        
        -   `httpClient.ts` 定义了两个 Axios 实例：`apiClient` 用于与主认证服务交互（Cheese-Auth相关接口），`sandboxClient` 用于与竞技后台交互[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L18-L26)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L27-L35)。它为 Axios 配置了请求拦截器，在每次请求头中自动附加当前用户的授权JWT令牌[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L94-L102)；响应拦截器则统一处理401未授权错误，通过调用刷新Token接口获取新Token并重试请求，实现透明的登录态续期[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L133-L142)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L148-L157)。此外还对HTTP 429（请求过多）错误封装为自定义 RateLimitError，以便上层识别并处理重试[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L164-L172)。
            
        -   `sandboxService.ts` 提供调用竞技后端各项功能的**封装方法**。如 `getSubmitters()` 调用 GET `/players` 获取所有参赛者列表[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L28-L36)；`submitCode(file)` 调用 POST `/compile` 上传源代码文件并返回任务ID[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L43-L51)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L59-L64)；`submitBatchExecution(requests)` 调用 POST `/execute/batch` 提交一批决策执行请求[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L129-L137)；以及 `listenToCompilationStream(jobId)` 和 `listenToExecutionStream(sessionId)` 方法建立 SSE 连接用于接收编译和执行过程的实时消息[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L74-L83)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L149-L157)。这些方法内部使用了前述 `sandboxClient` 实例，并对返回数据进行简单封装或错误处理，方便前端业务代码调用。
            
    -   **游戏辅助服务**：如 `FoodGenerator.ts`（食物生成器，根据游戏进程算法随机生成一定数量的各种食物/道具并避免与蛇或障碍重叠），`gameRecordingService.ts`（游戏录像服务，用于在前端记录对局过程帧数据，支持保存与加载录像文件），`Random.ts`（封装了可重复播种的随机数生成，用于确保比赛在给定种子下结果可重现）等工具模块。
        
    -   **配置与常量 (`src/config/GameConfig.ts`)**：定义游戏的重要参数和默认常量。例如最大玩家数量、地图尺寸（行数列数）、初始蛇长度、各种食物类型及生成规则、护盾的持续时间和冷却、总回合数等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/config/GameConfig.ts#L23-L31)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/config/GameConfig.ts#L34-L42)。其中还包括一些特定系统的开关和参数：如 **涡流场**功能开关和触发概率[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/config/GameConfig.ts#L46-L54)、**宝箱**出现时间配置、**食物生成策略**（分早期/中期/晚期调整不同类型食物权重）等。这些配置集中管理，方便根据比赛需求调整游戏难度和平衡性，也支持扩展新的地图或道具时在此增加配置项。维护者可以通过修改配置常量来快速调整游戏规则（例如将 `VORTEX_FIELD.ENABLED` 设为 false 以关闭涡流场特殊事件[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/config/GameConfig.ts#L46-L54)）。
        
-   **公共静态文件**：`public/` 目录下包含前端应用的静态资源和配置文件。例如 `index.html` 主页面模板、`config.js` 前端运行时配置（Docker部署时用于注入后端服务URL）、以及选手算法模板代码文件等。部署时这些文件会一并打包或复制到构建输出中。
    

综上，前端代码组织清晰——UI层、逻辑层、服务层分离。文件命名和目录划分具有自解释性，新开发者可以按功能模块逐步阅读源码，快速理解各部分职责。

## **状态管理机制**

前端作为比赛对局运行的主要驱动，需在浏览器中实时维护整个游戏的**状态数据**，并保证与后端决策计算的交互正确同步。以下详细说明前端的状态管理方式：

-   **游戏主状态与循环**：每场对局由前端创建一个 `GameManager` 实例管理。`GameManager` 内部维护了当前对局的所有状态对象（如实体列表、计时器、随机数种子等），并持有一个唯一的 **对局Session ID** 标识该场比赛（在构造时生成的 UUID）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L49-L53)。启动游戏时，GameManager 会首先调用 `prepareGame()` 进行初始化：清空上一场遗留状态，重置计时器和各种系统，然后通过实体工厂创建初始蛇列表和其他元素，将它们加入实体管理器中[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L189-L198)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L200-L208)。初始化完成后，GameManager 会向UI发送初始状态，例如触发计分板更新显示所有参赛蛇及其初始得分0[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L230-L238)、倒计时面板显示总回合数等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L230-L238)。**注意**：平台默认每局游戏**总Tick数**为固定值（例如256回合）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/config/GameConfig.ts#L23-L31)，GameClock将根据该值计时倒计时。
    
    GameManager 调用 `startGame()` 时会启动**游戏主循环**：其中利用 `GameClock` 设定的定时器按固定间隔触发每个Tick的更新（默认每500ms一个Tick，可通过配置调整节奏[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/config/GameConfig.ts#L40-L44)）。每次 Tick 都执行 `GameManager.updateTick()` 方法，它是游戏状态推进的核心逻辑。该方法按预定顺序执行了一系列更新步骤：
    
    1.  **更新环境效果**：例如涡流场 (`vortexFieldManager.update`)、安全区 (`safeZoneManager.update`) 和宝箱系统 (`treasureSystem.update`)都会根据当前Tick调用各自逻辑，决定是否影响游戏环境[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L333-L341)。这可能会更改内部状态，比如安全区半径缩小，或触发某个位置出现涡流拉扯效果等。
        
    2.  **组装游戏状态快照**：收集本Tick需要提供给AI决策的**完整环境信息**，包括所有实体（蛇的位置、长度、得分等，食物和障碍物坐标及类型，宝箱/钥匙状态）、当前涡流场参数、安全区范围等，然后序列化为结构化数据[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L214-L224)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L226-L235)。在实现中，这由 `GameManager.assembleGameState()` 完成，返回一个 `GameState` 对象供后续使用。
        
    3.  **获取所有蛇的决策**（异步）：对于每条存活的蛇，前端根据其**决策策略**执行行动决定。通过 EntityManager 提供的 `getAllSnakeDecisions(gameState)` 方法，遍历每条存活蛇调用其 `snake.update()` 方法[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L365-L373)。对于AI或API控制的蛇，这将进入对应策略的 `makeDecision` 实现：
        
        -   **API策略决策**：`APIDecisionStrategy` 会调用前述 `DecisionRequestCoordinator`，将当前游戏状态序列化为文本输入，并与该蛇所属用户ID一起组成执行请求[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L226-L235)。多个蛇的请求被协调器批量收集后，通过 `sandboxService.submitBatchExecution` 一并发送给后端执行[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L135-L144)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L146-L154)。协调器在首次发送时建立**SSE长连接**订阅该场对局的执行结果流，一旦后端运算完毕通过SSE推送结果，协调器即可解析对应`clientRequestId`找到匹配的蛇决策Promise并resolve[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L140-L149)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L186-L190)。在前端实现上，所有蛇的决策Promise通过 `Promise.allSettled` 并行等待[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L381-L389)，确保在进入下一步前**已收到或处理完每条蛇的动作决定**（若个别蛇超时或出错，Promise会以rejected完成，并在后续逻辑中将该蛇判为死亡）。
            
        -   **玩家/本地AI决策**：若蛇策略为玩家控制或本地AI，则决策在前端同步完成。例如玩家策略读取之前缓存的按键，将方向或护盾指令应用于蛇对象；本地AI策略则直接运行一段算法脚本计算方向。无论哪种策略，整个决策阶段对所有蛇是**并发异步**处理的，不阻塞UI渲染，并利用事件机制处理异常情况（如决策抛出错误则发送 `SNAKE_KILL_REQUEST` 请求清除该蛇[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L270-L275)）。
            
    4.  **应用决策并移动蛇**：当所有蛇决策获取完毕后，游戏进入**状态更新阶段**。首先，由 EntityManager 执行 `applyDecisionsAndMoveSnakes()` 方法，将每条蛇决定的动作付诸实现[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L341-L348)。具体而言，对每条存活蛇：
        
        -   如果蛇决定开启护盾（决策值为4），则调用蛇对象的 `activateShield()` 方法开启护盾状态（此时蛇本回合跳过移动，用护盾换取暂时无敌）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L46-L55)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L58-L66)。
            
        -   否则，读取蛇决策的方向值（0-3对应上/下/左/右），调用蛇对象的 `setDirection` 更新运动方向，然后调用 `snake.move()` 根据新方向移动位置[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L260-L264)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L261-L269)。移动逻辑由 Snake 类封装：将蛇身体坐标向前推进一个单元格（在网格中每格20px，对应GameConfig的BOX\_SIZE），尾部去除最后一格（除非吃到食物会在后续逻辑处理增长），并处理是否撞墙出界[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L170-L178)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L180-L188)。如果蛇此时处于护盾激活刚结束状态，会根据规则跳过移动以消耗护盾持续时间[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L170-L178)。
            
        -   EntityManager在每条蛇移动后，会同步更新空间哈希网格中蛇身体各段的位置映射[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L396-L405)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L411-L419)。通过对比移动前后的身体坐标，移除尾部出栈的坐标点，插入新的头部坐标，实现对局部区域的网格更新[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L413-L422)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L424-L432)。
            
    5.  **碰撞检测与处理**：蛇移动后，系统需要检测各类碰撞事件：
        
        -   **阶段1碰撞**：首先进行**蛇移动导致的直接碰撞**检查[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L347-L355)。这包括：蛇与食物碰撞（吃到食物）、蛇头与障碍/墙碰撞、蛇与蛇相撞以及蛇撞到自己或他人身体等情况。由 CollisionDetector 根据最新位置计算碰撞列表。如果碰撞结果包括**吃食物**，则 EntityManager 将调用蛇对象增加得分、增长身体长度等；如果是**撞墙/撞蛇**等致命碰撞，则不会立即移除蛇，而是触发该蛇进入死亡动画状态（isDying），由动画系统和事件总线协调死亡过程。此处采用**延迟处理**策略：GameManager调用 `handleCollisionsWithDelay` 方法，对碰撞结果作初步标记，但给予短暂时间用于在画面上表现碰撞（例如显示撞击效果）后再正式结算[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L352-L360)。死亡动画开始时，蛇仍被保留在场景中一段时间（isDying=true但isAlive=false），待动画播放完毕后Snake类会发送 `SNAKE_DEATH_ANIMATION_COMPLETE` 事件[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L152-L160)，EntityManager监听到后真正将蛇移出游戏并清理资源[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L61-L69)。这种设计保证了**视觉效果与逻辑同步**，不会因为立即移除对象而错过碰撞瞬间的显示。
            
        -   **特殊机制更新**：在处理完移动和初步碰撞后，GameManager继续执行一些特殊机制影响。例如如果**涡流场**功能启用且在活动期，调用 `applyVortexPull()` 对尚未死亡的蛇施加额外位移[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L356-L364)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L359-L367)。涡流场会根据蛇头所在区域计算一个拉力方向，将蛇整体往该方向移动一个单位（通过修改蛇身体坐标实现，类似一帧特殊移动）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L359-L367)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L373-L381)。紧接着进行**阶段2碰撞检测**（针对涡流位移后的状态），如有新的碰撞则处理之（例如被涡流拉动后导致两蛇碰撞等）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L361-L369)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L371-L379)。
            
        -   **安全区检查**：最后，GameManager调用 `checkSafeZoneViolations()`，遍历所有仍存活且未在死亡动画中的蛇，检查其头部是否在当前安全区范围内[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L373-L381)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L376-L384)。若有蛇已脱离安全区且没有护盾保护，则判定其“淘汰”：触发宝箱/钥匙掉落逻辑（TreasureSystem处理该蛇持有钥匙掉落在原地），随后将该蛇立即标记死亡[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L422-L430)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L436-L445)。安全区机制通常在后期收缩地图提高竞争激烈度，离圈的蛇会被逐步淘汰。
            
    6.  **生成新元素**：在处理完碰撞和淘汰后，本回合接近尾声，GameManager会调用食物生成逻辑产生新的道具：
        
        -   首先利用 `FoodGenerator.generatePeriodicFood(currentTick)` 在当前Tick随机尝试生成若干新食物[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L377-L385)。FoodGenerator会参考GameConfig中设定的生成目标和权重，可能产生不同价值的普通食物、增长豆或陷阱食物等，并确保位置不与现有实体冲突。函数返回新生成的食物列表后，GameManager将这些食物加入实体管理器[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L379-L387)。
            
        -   调用 `EntityManager.updateFoodLifecycles()` 更新场上所有食物的生命周期倒计时（某些食物存在TTL，超时会自动消失），并清理过期的食物[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L379-L387)。这样游戏地图上的资源会动态刷新、保持平衡。
            
    7.  **记录与渲染**：如果当前开启了**录像记录功能**（由GameManager初始化时的参数决定），则在每个Tick结束时调用 `gameRecordingService.recordFrame()` 保存当前帧的完整状态[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L383-L391)。录像数据包括Tick编号以及GameState序列化结果，必要时还记录安全区信息，用于回放还原。最后，GameManager一次逻辑Tick更新结束，控制流返回等待下一个Tick触发。需要强调的是：**游戏画面的渲染与逻辑更新是解耦的**[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L389-L395)。CanvasManager通过`requestAnimationFrame`实现独立的 `renderLoop()`，通常以每秒60帧的频率持续绘制[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L814-L823)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L852-L860)。渲染循环每帧获取当前所有实体位置来绘制，并根据需要绘制一些叠加信息（如暂停时的半透明遮罩、游戏结束时的提示等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L852-L860)）。由于渲染频率高于逻辑Tick频率，蛇的移动采用插值动画实现平滑过渡：Snake对象维护了移动进度`moveProgress`，在每帧根据上次Tick到当前的时间差增量更新，用于插值计算身体位置[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L132-L140)。死亡动画类似地通过`deathProgress`推进透明度或缩放效果[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/entities/Snake.ts#L146-L155)。CanvasManager每帧调用 EntityManager 的 `updateAnimations(deltaTime)`，后者迭代蛇列表执行上述进度更新，以驱动动画[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L444-L452)。因此，即使逻辑每500ms更新一次，画面依然每帧平滑渲染，提供良好观感。
        
-   **状态同步与前后端交互**：前端通过**事件和回调**机制，实现游戏状态与后端执行结果的同步：
    
    -   **决策请求协同**：DecisionRequestCoordinator 承担了在**单个Tick内批量协调多个后端执行请求**的任务。每当APIStrategy需要获取决策时，它调用 `coordinator.requestDecision(item)` 将请求入队[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L48-L56)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L68-L76)。Coordinator使用一个短暂的microtask延迟将同一Tick内收集到的所有请求一起发送[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L72-L80)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L114-L122)。发送前会为每个请求生成一个唯一的 `clientRequestId`（通常用 **用户ID-剩余Tick数** 形式标识）并保存对应Promise的resolve方法，以便后续匹配结果[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L202-L210)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L228-L237)。首次发送时通过 `listenToExecutionStream(sessionId)` 打开 SSE 连接监听此对局ID的执行结果事件流[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L140-L149)。**后端Controller** 会对每个执行任务在完成时推送 SSE 消息，Coordinator收到事件后解析其中包含的 `clientRequestId`，据此找到对应Promise并调用resolve传回结果数据[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L186-L190)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L48-L56)。为保证一致性，后端SSE发送的是统一的JSON消息（字段包括jobId、eventType、status、输出等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/types/Api.ts#L24-L32)），Coordinator对其中`eventType`进行判断，通常只处理最终结果（FINAL\_RESULT）事件，从而**以异步事件驱动的方式将后端计算结果注入前端逻辑**。如果在限定时间内某条蛇未收到决策结果（例如后端超时），Coordinator不会等待无限久：由后端判定超时并通过FINAL\_RESULT事件返回错误状态，前端同样会resolve Promise并在APIStrategy中发现`success=false`，触发将该蛇移出（视为算法失败被淘汰）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L270-L275)。整个流程保证每回合前端逻辑与后端计算**一一对应、同步推进**。
        
    -   **UI状态更新**：利用**事件总线**及时反映游戏状态变化到界面。例如每当蛇得分变化或死亡，EntityManager会在适当时机发送 `UI_UPDATE_SCOREBOARD` 事件携带最新蛇列表[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L230-L238)，计分板组件收到后重新排序展示；每过一个Tick，GameManager都会发送 `UI_UPDATE_TIMER` 事件更新剩余时间显示[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L230-L238)。碰撞、吃食物等事件则通过 `UI_NOTIFICATION` 事件发送文本描述，通知面板组件将其加入日志列表显示（实现中结合HTML模版高亮蛇名等）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/components/GameUILeft.vue#L74-L82)。此外，当游戏结束条件达成（如Tick耗尽或仅剩一蛇存活），GameManager会停止时钟并发送 `GAME_OVER` 事件，各UI组件据此弹出结算界面、提供再来一局或返回等选项。通过事件机制，**游戏数据的变化能够驱动UI自动更新**，而不需要界面组件主动轮询状态，提高了前端状态管理的可靠性和效率。
        
-   **本地持久化**：前端还承担了一部分状态的持久化功能，例如**对局录像**。当录制开启时，每个Tick结束时保存的GameState会暂存于浏览器内存，通过GameRecordingService在游戏结束时提供下载功能（JSON或二进制格式）。用户也可在游戏Rankings弹窗中选择保存录制[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L276-L284)。这些录像文件日后可在 `GameReplay.vue` 页面加载回放。Replay模块会利用录制的每帧状态数据，驱动一个专门的 `GameReplayManager`（继承自GameManager或类似逻辑）以比实时更快速度重演比赛。这种机制为选手调试算法和赛后分析提供了极大便利，也是前端在状态管理上的扩展功能。
    

综上，前端通过**面向对象的数据模型+主循环驱动**实现了完整的贪吃蛇对战模拟。借助事件总线和Promise异步处理，保证了浏览器中游戏状态与后端AI决策结果的严密同步。同时，合理划分多阶段更新与动画渲染，使得即使规则复杂、玩家众多，前端也能高效维护状态并提供流畅的可视化效果。

## **核心流程**

本节通过几个关键流程的步骤说明，帮助理解前端在典型场景下的工作方式：

### **1\. 房间创建与游戏开始流程**

“房间”指一次对战会话，由用户在前端发起，包括选定参赛AI、创建游戏并驱动其运行。流程如下：

1.  **选择参赛蛇**：用户登录后进入“开始游戏”页面（Game.vue）。页面加载时前端调用 `sandboxService.getSubmitters()` 拉取所有可选参赛者列表[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L28-L36)（通常为已成功编译代码的用户），并显示在左侧列表中。用户可通过点选名单或批量输入用户名来选择对战的AI，最多可选20个（受GameConfig.MAX\_PLAYERS限制[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L32-L40)）。选中的参赛者会显示在界面中部的已选列表，包括昵称、用户名等信息[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L46-L55)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L56-L64)。在需要时用户也可以指定一个随机种子（输入框）用于控制比赛的随机性，以便结果重现[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L110-L118)。
    
2.  **创建房间**：当至少选择了一名参赛蛇后，“开始游戏”按钮可用，用户点击后触发 `startGameWithSelectedUsers` 方法。该方法会切换界面状态（Game.vue的 `gameStarted` 由 false 变 true），从而隐藏选择面板、显示游戏对局界面[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L2-L10)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L149-L157)。此时组件会创建一个新的 `GameManager` 实例：构造时传入选中用户列表、随机种子等参数，并指定启用录像与否[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L178-L186)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L60-L68)。GameManager 在初始化过程中生成一个Session ID并完成前述`prepareGame()`（创建蛇、食物等）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L187-L196)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L200-L208)。前端并**不会请求后端创建房间**，因为比赛状态完全由前端维护，Session ID主要用于后端识别该对局执行流（例如 SSE 通道标识）。准备完成后，GameManager通过事件通知UI初始化状态（计分板、计时器）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L230-L238)，然后等待用户进一步指令。
    
3.  **开始对局**：GameManager 初始化完毕后，会自动或在用户确认下调用 `startGame()` 开始主循环[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L243-L252)。在Game.vue中，组件会订阅GameManager的全局事件（如GAME\_START、GAME\_OVER等）来控制UI元素，例如开始后隐藏“开始游戏”按钮/显示控制面板，结束后弹出结果窗口等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L156-L164)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L168-L175)。GameManager启动GameClock计时，每500毫秒触发一次Tick调用 `updateTick()` 进行游戏逻辑更新[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/GameManager.ts#L253-L262)。至此，对局正式开始，前端进入每回合Tick与后端交互计算的循环过程（详见下一流程）。
    
4.  **用户控制**：在对局过程中，如果有蛇被设置为玩家控制（通常选中列表的第一条蛇可以预留给当前用户控制），前端捕捉用户键盘输入来影响蛇决策。Game.vue 全局监听键盘方向键，将其转发给 InputHandler 及 PlayerDecisionStrategy[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/main.ts#L7-L15)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L19-L27)。例如，当玩家按下↑键，PlayerDecisionStrategy会记录方向“UP”，在下一个Tick被GameManager调用时应用给对应的蛇[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L40-L48)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L56-L64)。护盾激活键（如空格）也类似处理。一局游戏期间，玩家随时可以通过键盘干预自己蛇的动作，从而与AI对手竞争。
    

### **2\. 回合运行与决策请求流程**

每个游戏回合（Tick）前端都会执行游戏逻辑更新，并可能向后端请求AI决策。该流程持续进行，直到胜负产生或达到最大回合数。以**单个Tick**为例，其核心步骤和前后端交互如下：

1.  **收集环境输入**：GameManager触发Tick更新时，首先汇总当前游戏状态需要提供给AI算法的信息（即GameState）。其中包含：剩余时间Tick数、所有特殊物品（食物/障碍/宝箱/钥匙）的坐标及类型、存活蛇数量及每条蛇的长度、得分、当前朝向、护盾冷却/持续时间，以及每条蛇身体每节的坐标列表等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L338-L346)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L374-L382)。此外，如果有**宝箱**未被开启，附加其坐标和分值列表；如果有钥匙散落或被蛇持有，则汇总其位置、持有者ID及剩余保留时间等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L405-L414)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L436-L445)；以及**安全区**当前边界和下一次收缩信息[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L452-L460)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L462-L470)。这些数据最终序列化为一个文本块，以行为单位编码（遵循比赛规则预定的输入格式）。例如，文本开头是剩余Tick数和物品数量，接下来若干行列出每个物品的 `y x value ttl`，再列出存活蛇数及每条蛇的基本信息和身体坐标……一直到安全区的三行参数[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L338-L346)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L374-L382)。前端通过 `formatGameStateForAPI` 函数完成此序列化[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L214-L224)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L226-L235)，保证和后端判题逻辑期望的输入格式一致。
    
2.  **发送决策请求**：对于本回合需要后端决策的蛇（即采用APIDecisionStrategy的蛇），前端将为每条蛇生成一个执行请求对象，包括所属用户ID、上一步组装的输入数据字符串、该蛇本地生成的clientRequestId、所属Session ID以及当前Tick编号等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L226-L235)。这些请求通过 DecisionRequestCoordinator 进行批处理：Coordinator会将多个请求临时存入队列并在同一事件循环周期合并发送，以减少HTTP开销[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L72-L80)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L114-L122)。发送时调用 `sandboxService.submitBatchExecution`，目标接口为 **POST** `/execute/batch`，请求体是上述请求对象数组[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L129-L137)。后端Controller收到后，会为每个请求分配执行任务（利用用户上传的可执行程序），并立即返回202 Accepted状态和任务信息，其中包含一个全局 **sessionId** 供后续追踪[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/types/Api.ts#L36-L44)。前端Coordinator在第一次发送时，从响应中提取sessionId并调用 `sandboxService.listenToExecutionStream(sessionId, fromTick=0)` 建立 SSE 连接订阅该session的执行事件[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L140-L149)。
    
3.  **异步获取执行结果**：后端执行各AI程序可能需要数百毫秒到数秒不等。为避免阻塞前端，Coordinator已经在发送后立即返回一个Promise，并通过SSE监听结果。当某个AI代码运行完毕，后端Worker会通过消息队列通知Controller，然后由Controller推送 SSE 事件到前端。事件数据被Coordinator接收后，提取出其中clientRequestId（即前端当时发送请求时附带的键）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L46-L54)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L50-L58)。Coordinator在内部映射表中找到对应clientRequestId的Promise resolver，将结果解析成标准结构后调用resolve，完成该Promise[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L50-L58)。这样，在GameManager等待的 `getAllSnakeDecisions()` 方法中，之前await的Promise就会被解除阻塞[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L365-L373)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L381-L389)。Coordinator处理每条消息都会相应地resolve一条蛇的决策Promise；当一回合中所有蛇结果都抵达（或超时失败）后，GameManager即可继续后续逻辑。
    
4.  **应用决策**：GameManager恢复执行后，对于每条蛇检查其决策结果：
    
    -   如果决策成功且输出有效，如 `"UP"`, `"LEFT"` 等，APIDecisionStrategy会将其转换为0-3的方向值或者4（盾）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L261-L269)并调用 `snake.setDirection` 或 `snake.activateShield` 应用动作[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L261-L269)。同时将该输出以及程序运行耗时、内存等信息存入Snake的元数据（metadata）以备查询[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L247-L255)。
        
    -   如果决策结果指示失败（超时TLE、运行时错误RE等）或者输出为空/格式不合法，前端判定该蛇本回合**无有效动作**。按照平台规则，此情况下蛇会被直接淘汰：APIDecisionStrategy捕获到这种情形后，通过事件总线发出 `SNAKE_KILL_REQUEST` 请求GameManager移除该蛇[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L270-L275)。EntityManager监听到该事件后，会立刻调用其 `killSnake(snake, reason)` 方法标记该蛇死亡并安排清理[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/managers/EntityManager.ts#L80-L88)。这样可以防止“不作为”的蛇影响比赛公正性。Snake死亡的具体过程将按照上一节描述（死亡动画->完成后彻底清除）进行。
        
    -   如果 SSE 连接中断或出现异常情况，Coordinator会catch到错误并reject所有等待的Promise[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L60-L64)。APIDecisionStrategy的makeDecision中有对应catch逻辑，一旦Promise被reject，同样发出 `SNAKE_KILL_REQUEST` 淘汰相关蛇[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L276-L284)。Coordinator之后也会尝试重连SSE（实际实现中RateLimitError触发指数退避重试[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L160-L169)），尽量保证对局不中断。
        
5.  **更新画面与下一回合**：决策应用后，本回合剩余逻辑如移动蛇、碰撞处理、生成食物等按上一节状态管理机制执行。画面通过CanvasManager渲染当前帧。如果比赛尚未结束，GameClock会在下一个时间点触发新的Tick，重复上述过程。**值得注意**：由于前端采用了**乐观并行**策略发送决策请求，实际后端执行与前端逻辑存在轻微并发——即前端一个Tick的逻辑可能尚未完全结束，后端可能已经在计算下一个Tick决策。因此必须确保**每个Tick严格按顺序处理**：Coordinator的设计和Session隔离保证了事件顺序，后端也以Session+Tick为键序列化执行顺序，所以不会出现乱序。前端只有在Tick结束时才会触发下一轮请求，从而维持稳定的状态同步。
    

整个回合流程体现了前端与后端紧密配合：前端驱动节奏并维护游戏规则，后端在关键步骤提供AI决策算力。两者通过HTTP+SSE双向通信实现了**近乎实时**的交互（每回合几百毫秒内完成）。对于用户而言，这一切都是透明的：他们看到的只是蛇在地图上不断移动、竞争，背后复杂的协调都由前端代码自动完成。

### **3\. 源码提交与编译流程**

在比赛平台中，源码提交和编译是选手交互的重要环节。前端提供了提交代码并监视编译结果的功能，其流程如下：

1.  **上传代码**：选手进入“提交代码”页面（SubmitCode.vue），选择源代码文件（目前通常是 C++ 程序，如一个`*.cpp`文件）。前端读取文件后，通过 `sandboxService.submitCode(file)` 调用后端 **POST** `/compile` 接口上传[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L43-L51)。该请求以FormData形式发送文件内容，后端Controller收到后创建编译任务。前端在发送请求时可以提供onUploadProgress回调以更新上传进度条（例如以百分比显示上传进度）[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L50-L58)。
    
2.  **返回任务ID**：后端同步返回一个JSON响应，包含状态码和分配的编译任务ID。若返回HTTP 202且data中带有jobId，表示编译任务已成功提交进入队列[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L59-L64)。前端从响应中提取 jobId，接下来使用它建立SSE连接监听编译过程。
    
3.  **实时编译输出**：前端调用 `sandboxService.listenToCompilationStream(jobId)` 来创建 SSE连接[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L74-L83)。该方法使用 SSE.js 库连接到 `/compile/stream/{jobId}` 端点，并附带认证Bearer Token[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L79-L85)。建立连接后，会监听两类事件：
    
    -   未命名的默认`message`事件：后端在编译过程中可能推送若干状态更新（如编译日志或进度消息），前端统一处理这些消息，将其内容（一般是字符串日志）传给提供的 onEvent 回调[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L86-L95)。SubmitCode组件可能将这些日志逐行显示，供用户了解编译发生了什么（例如编译错误信息）。
        
    -   特定`FINAL_RESULT`事件：标志编译任务完成的最终结果。前端对该事件数据进行JSON解析，如果编译成功，数据中可能包含可执行文件信息或成功标识；如果失败，则包含错误消息。无论成功与否，前端都会据此更新页面状态：成功则提示编译通过，可以进行下一步操作；失败则将错误信息展示给用户并允许重新提交。
        
4.  **关闭连接**：编译一旦结束（收到FINAL\_RESULT），前端会关闭SSE连接释放资源[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L100-L108)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L114-L120)。SubmitCode页面根据最终结果进行UI反馈，例如弹出“编译成功”提示或高亮错误详情。此外，为保持系统状态一致，编译成功后后端通常会将用户的最新代码记录标记为“可用”，前端稍后刷新参赛者列表时即可反映该用户状态变化（如`lastUpdate`时间）。
    
5.  **结果生效**：一旦代码编译成功，选手即可在对战页面选择该参赛者参加比赛。前端的玩家列表 `availableUsers` 就会包含新提交代码的用户，且其 lastUpdate 字段更新为刚刚的编译时间[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L94-L101)（此信息由后端/数据库提供）。这体现了前后端协同：**后端负责代码编译及存储**，**前端负责反馈结果并使用更新后的数据**。对于编译失败的情况，选手可以修改代码后再次提交，前端流程相同。
    

该流程确保了代码从上传到编译的过程对用户友好可见。通过 SSE 实时日志，选手能够**即时看到编译错误**而无需不断刷新查询，大大提升了体验。

_(注：选手源码的运行由后端Worker完成，前端不介入代码安全沙箱等细节，只通过后端接口使用编译/执行结果。后端编译逻辑详见后端交接文档相关章节，此处不赘述。)_

## **与后端交互说明**

前端通过 **REST API 请求** 和 **SSE 推送** 与后端各服务模块交互。主要交互点和协议如下：

-   **用户认证服务（Cheese-Auth）**：前端与认证后端的交互采用 REST API + 浏览器重定向方式。典型流程为：
    
    -   用户注册/登录：在登录页，若启用了学校OAuth，则跳转OAuth授权并由 `OAuthCallback.vue` 接收授权码，再请求 `/users/auth/oauth` 获取JWT Token；或使用用户名密码时直接调用 `/users/auth/login` 接口获取Token。成功登录后，将返回的 accessToken 存储到 `localStorage` 并写入 Axios 默认Header 中[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L70-L78)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L96-L101)。此后所有请求都带上 `Authorization: Bearer <token>` 头用于鉴权。
        
    -   刷新Token：在 httpClient 中封装了 `/users/auth/refresh-token` 刷新接口的调用[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L56-L65)，并通过响应拦截器自动处理过期Token。当任一API返回401且未重试过时，前端暂停当前请求，调用刷新接口获取新Token，成功后重试原请求[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L133-L142)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L148-L157)。若刷新也失败（如RefreshToken失效），则清除本地凭证并重定向登录页面[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/httpClient.ts#L120-L129)。这一机制保证了用户会话的连续性和安全退出。
        
    -   用户数据接口：`apiClient` 还用于获取用户资料（例如 `/users/me`）、排行榜等。如果有头像或其他资源，前端可能通过URL直接加载。这部分接口均受JWT保护，前端依赖认证服务验证Token有效性。
        
-   **竞技平台主服务**：主要指 **Sandbox 后端服务**，负责比赛相关的数据和算法执行：
    
    -   **获取参赛者列表**：GET `/players`，前端调用后端Controller获取所有已注册并有可用编译程序的用户列表。响应一般包含每个用户的 `userId`, `username`（学号或账户名）, `nickname`（昵称）, `avatarId`（头像资源ID）以及 `lastUpdate`（最近编译时间）等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/types/User.ts#L16-L24)。前端据此展示名单并可能按照更新时间排序（最新编译的在前等），以便选择活跃的算法。
        
    -   **代码编译接口**：POST `/compile`，用于提交源码文件。前端构造表单请求附带文件，需用户登录授权。后端响应202 Accepted表示任务受理，并返回 `jobId`[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L59-L64)。前端接着通过 SSE 获取编译进度/结果：连接 `/compile/stream/{jobId}`，通常后端会推送若干文本消息（编译输出、错误等）以及最后的`FINAL_RESULT`事件指示编译成功或失败[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L74-L83)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L86-L95)。消息的数据结构与后端 `JobSseEvent` 定义一致，一般包含 `eventType`（如STATUS\_UPDATE, FINAL\_RESULT）、`message`或`data`字段携带信息[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/types/Api.ts#L24-L32)。前端对这些事件逐一处理，更新UI。**注意**：编译SSE连接需要认证，前端在建立时会从 localStorage 取出JWT附加在请求头上[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L79-L85)。后端据此验证权限，没有有效Token将拒绝连接（前端监听SSE的 error事件处理此类错误[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L100-L108)）。
        
    -   **执行任务接口**：POST `/execute/batch`，用于提交一回合中多个算法决策执行请求。前端每回合调用一次，传递JSON数组，其中每项包含 userId, inputData（游戏状态输入字符串，可能较长）, clientRequestId（前端生成的唯一键）以及资源限制等[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/strategies/SnakeDecisionStrategies.ts#L226-L235)。后端收到后，将每项任务入队执行，立即返回202以及任务汇总信息[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/types/Api.ts#L36-L44)。前端Coordinator不直接使用返回内容（除了获取sessionId），而是通过 SSE 获取执行结果：
        
        -   SSE连接 `/execute/stream/{sessionId}?fromTick=X`：该连接按比赛对局Session订阅所有执行结果事件。为了保证即使前端偶发断线也不遗漏消息，API支持指定 fromTick 参数从特定Tick编号开始发送历史事件[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L149-L157)。Coordinator通常在首次建立连接时 fromTick=0 以接收整场比赛的事件，之后保持连接不断开，后端将持续推送新的结果。
            
        -   **事件结构**：执行SSE事件的数据结构与编译类似，使用统一的 SseEventData DTO[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/types/Api.ts#L24-L32)。其中 `eventType` 常用 "FINAL\_RESULT" 表示某任务完成，其 `data` 字段内包含该任务对应的clientRequestId、算法输出、状态码等信息[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/types/Api.ts#L24-L32)。Coordinator监听到事件后据 data.clientRequestId 查找对应Promise并resolve结果[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L44-L52)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L68-L71)。为稳妥起见，Coordinator对任一session只建立一个SSE连接，共享接收所有蛇结果；如果连接意外关闭会尝试重连（实现中可扩展，例如根据错误类型决定是否整场比赛中止）。
            
        -   **触发时机**：该接口的调用由 GameManager 在每个Tick开始时触发（通过DecisionRequestCoordinator间接调用）。前端不会主动调用 `/execute` 接口，因为单个算法执行也包装在batch接口中处理。可以理解为：**前端每推进一回合，就触发一次向后端批量请求AI决策**，然后异步等待SSE返回。这种模式减少了网络交互次数，并充分利用后端并行执行能力，加快了回合响应速度。
            
    -   **其他接口**：平台还可能提供如 GET `/records`（获取历史比赛记录列表）、GET `/records/{id}`（获取特定比赛的录像数据）等接口，供前端的录像列表和回放功能使用。再如 GET `/rules`（获取比赛规则说明），也许用于规则页面展示。这些接口通常返回JSON数据，前端调用后直接用于渲染或下载。例如GameReplay.vue在加载录像时，可能通过 API 获取指定session的完整对局数据，然后使用GameReplayManager解析播放。
        
-   **通信细节与安全**：前端所有与后端的HTTP请求均通过HTTPS（若部署开启）并带JWT验证。Nginx会将 `/api/cheese-auth/**` 的请求转发至认证服务，`/api/sandbox/**` 转发至竞技服务，使前端调用统一以 `/api/...` 开头即可。SSE连接由于是基于HTTP的长连接，也遵循同域安全策略：前端使用的sse.js库允许传入自定义Header以附加Bearer令牌[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/services/sandboxService.ts#L79-L85)，这样后端可校验权限后建立流。需要注意的是浏览器对SSE每个域名默认**限制6个并发连接**，前端目前每场比赛用1条执行SSE，编译用1条SSE，数量有限，不会触发浏览器限制。前端对断线重连的策略也很谨慎：如遇网络抖动，sse.js会触发error事件，Coordinator捕获后可选择重连或中止比赛[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L156-L164)[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/core/DecisionRequestCoordinator.ts#L170-L178)。这些都封装在底层，对上层GameManager是透明的。总的来说，前后端通过REST完成一次性指令，通过SSE完成实时数据推送，结合使用确保了既能可靠请求操作又能高效获得异步结果。
    

## **本地开发与部署指南**

本节提供前端项目的开发和部署方法，方便新维护者快速上手：

### **开发环境准备**

1.  **Node.js 与包管理器**：确保安装 Node.js（建议使用≥16.x或更高版本，与项目所用 Node 22 Alpine 镜像兼容）。本项目使用 **pnpm** 作为包管理工具，首次运行前请通过 `npm install -g pnpm@9` 安装对应版本的pnpm。[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/Dockerfile#L2-L5)
    
2.  **克隆代码仓库**：从版本管理系统获取 `snake-frontend` 仓库代码，并进入项目根目录。
    
3.  **安装依赖**：运行 `pnpm install`。pnpm会根据 `pnpm-lock.yaml` 锁定版本安装依赖，确保与线上环境一致[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/Dockerfile#L4-L8)。成功后，`node_modules` 将准备就绪。

### **项目结构与编译**

-   本项目是基于 Vue3 + TypeScript + Vite 的单页应用（SPA）。源码主要在 `src/` 目录下，使用单文件组件（\*.vue）组织。开发者可以使用 VSCode 等支持Vue的编辑器以获得语法高亮、类型检查和实时预览。
    
-   构建脚本：`package.json` 定义了常用脚本，如：
    
    -   `pnpm run build`：执行项目构建，先运行 TypeScript 类型检查（`tsc`）再用 Vite 打包[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/package.json#L6-L9)。打包结果输出到 `dist/` 目录，包含优化压缩后的HTML、JS、CSS和静态资源。构建过程中还使用了 `vite-plugin-compression` 插件，直接生成`.gz`压缩文件便于服务器开启gzip。[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/package.json#L14-L18)
        
    -   `pnpm run preview`：使用Vite本地预览服务器在构建后提供静态文件预览，通常用于本地检查生产环境下的打包效果。
        
-   TypeScript：项目配置了严格的TS类型定义，`src/env.d.ts` 和 `src/runtime-config.d.ts` 声明了一些全局变量类型，开发中应充分利用TS的提示减少错误。构建时`tsc`会做类型检查，如有错误需先修复。
    
-   代码风格：团队可自行约定，项目中未见显式ESLint配置，但建议遵循已有代码格式（4空格缩进、CamelCase命名等）。可考虑引入Prettier/ESLint保证一致性。

## **运行环境要求**

-   **浏览器要求**：平台前端在现代浏览器上运行良好。推荐使用**Chrome 100+、Firefox 100+、Edge 100+** 或同等版本的浏览器。Vue3不再支持IE浏览器，因此**不兼容IE11及以下**。Safari (14+) 基本兼容，但由于涉及键盘控制和Canvas绘制，建议使用PC端浏览器体验最佳。移动端浏览器（Chrome Mobile, Safari iOS等）可加载页面但操作性和显示效果可能不如桌面端。前端大量使用了ES6+语法（如`Promise`、`async/await`）和Web标准API（如 `EventSource`用于SSE），所以上述浏览器版本均需支持这些特性 —— 幸而当前主流浏览器都已支持。
    
-   **操作系统兼容**：与浏览器相关，前端不依赖任何特定操作系统功能。Windows、macOS、Linux桌面环境皆可流畅运行，只要有支持的浏览器。开发过程中在 Windows 10/11, Ubuntu 20.04+, macOS Monterey 环境均经过测试，无明显差异。对于服务器端部署，前端只是静态文件，可以托管在Linux (如Ubuntu/CentOS)或任何支持Docker的平台上。
    
-   **性能需求**：前端需要一定的客户端硬件性能。由于**游戏状态完全在浏览器计算**，当参赛蛇数量较多（比如同时20条蛇）或开启了复杂特效（涡流场、粒子效果等），浏览器需要处理较频繁的绘图和大量对象计算。一般来说，一台配备中档CPU的电脑（如 Intel i5 第8代 或同等AMD CPU）即可确保比赛动画流畅。如果使用较老旧的设备或低端移动端，可能在大量对象渲染时出现掉帧。维护者可以在测试环境中尝试最大负载情况评估帧率，以便给参赛者提供最低硬件建议。
    
-   **第三方库依赖**：前端运行时依赖的第三方库包括：

综合来看，前端对运行环境的要求是**常见Web应用的标准要求**：现代浏览器和正常网络。维护者在更新前端技术栈时，应关注可能的兼容性变化（如Vue后续版本要求更高的浏览器版本等）。目前配置下支持的平台已经覆盖绝大部分终端。

## **扩展性设计**

平台前端在设计时充分考虑了未来的扩展需求，体现为以下几方面：

-   **游戏规则和元素的可扩展**：代码采用了模块化、配置化的结构，使得增加新游戏元素或改动规则相对容易。GameConfig集中定义的参数允许快速调整**地图大小、回合数、食物种类、道具效果**等。例如要新增一种特殊食物或道具，只需：
    
    1.  在 GameConfig 中增加对应类型常量和生成规则；
        
    2.  创建新的实体类继承自基础 Entity，封装该道具的特性；
        
    3.  在 FoodGenerator（或类似生成器）中加入生成逻辑；
        
    4.  在 CollisionDetector 中添加对该道具碰撞的处理分支（或复用已有框架，例如宝箱/钥匙就是类似流程）；
        
    5.  在 CanvasManager 和渲染器中添加绘制支持（指定颜色或图片）；  
        如此便可将新元素融入游戏循环。前端已有宝箱、钥匙、涡流场、护盾等复杂元素作为示例，这些特性都通过松耦合组件插入而没有影响主流程。例如涡流场功能可以通过 GameConfig 开关完全禁用或启用[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/config/GameConfig.ts#L46-L54)，对其他系统几乎无侵入性；宝箱/钥匙系统则通过TreasureSystem集中管理，游戏主循环在恰当时机调用，不影响基本蛇与食物逻辑。这种设计说明**新增一个类似独立系统**（比如“毒雾”机制）时，可以仿照宝箱系统开发，主循环挂载调用，彼此独立又协同。
        
-   **水平扩展能力**：由于前端主要在客户端浏览器运行，理论上**增加用户不会增加单个前端实例的负载**。每位用户的浏览器承担自己的比赛模拟，后端可以通过增加Worker节点扩展计算能力。所以系统瓶颈主要在后端。前端部署可以使用CDN或多实例无状态扩容来同时服务大量访问者。换言之，**前端天然具备水平扩展性**，维护者只需确保静态资源可以快速分发、适当做缓存，前端就能支持更多比赛并发而无需修改代码。对于单场比赛涉及的前端性能瓶颈（比如20条蛇AI导致浏览器计算压力大），可通过提升客户端硬件或调整每回合间隔来缓解，或者未来将部分计算放到Worker线程等优化方向。
    
-   **多模式支持**：前端已经实现了**多人FFA（Free-For-All）对战**和**锦标赛**两种模式。Tournament模块展示了利用前端逻辑批量运行多场比赛以完成淘汰赛/循环赛等的可能：它可以调用 GameManager 多次或维护一个比赛日程，在每场之间衔接结果。这证明前端架构不局限于单场对战，可以扩展出**赛制管理层**。未来若增加**团队赛**、**挑战模式**等，也可在前端增加相应页面和管理逻辑，然后复用底层GameManager来跑具体对局。路由和组件结构支持并行存在多个功能模块，互不冲突。
    
-   **算法支持的扩展**：目前平台主要面向单一语言（例如C++）的算法竞技。如果将来需要支持**多种语言**或**更多AI实例**，前端基本无需改动：选手代码语言是后端编译执行的事情，前端提交和获取结果接口可以保持一致；AI数量扩展只要不超过前端界面布局可承载范围（当前UI限定20条蛇，可通过修改样式和配置提升此限制[GitHub](https://github.com/SageSeekerSociety/snake-frontend/blob/eb552d14f2c4d80fb7f3cf095246f9b87eceb2ae/src/views/Game.vue#L32-L40)）。DecisionRequestCoordinator基于每蛇每Tick请求，不关心代码语言，实现上也已考虑了批量与并发，不会成为瓶颈。唯一需注意的是：如果有超过几十条AI同时比赛，前端Canvas绘制和碰撞计算复杂度会增加，可能需要进一步优化算法或借助GPU。但这属于性能调优范畴，不影响架构。
    
-   **松耦合和可维护性**：前端充分利用**事件驱动**和**策略模式**来降低各部分依赖。UI与游戏逻辑通过事件总线通信，使UI改版或新增界面不会干扰核心逻辑，同样改变游戏规则也无需修改UI代码，只需发送的事件和数据保持格式。在策略模式下，添加一种新的蛇AI控制方式不会影响Snake或GameManager本身，只要符合 SnakeDecisionStrategy 接口即可插入使用。例如可想象未来支持**远程实时对战**（由真人手动操控蛇）：可以实现一个NetworkDecisionStrategy，从网络接收玩家控制指令，然后挂载给Snake，即可实现远程真人对战，现有框架无需大改。又比如，可以给SnakeDecisionStrategy添加一个 `pause()` 或 `resume()` 方法用于比赛暂停/恢复，GameManager调控它们即可全局生效。这种良好的可扩展性归功于接口设计和模块解耦。
    
-   **配置与开关**：GameConfig大量采用**常量配置+特性开关**模式，使快速定制不同比赛规则成为可能。例如，将 MAX\_PLAYERS 改小可以用于新人练习场，将TOTAL\_TICKS增大可以用于马拉松长赛；关闭TreasureSystem.ENABLED即可禁用钥匙宝箱玩法，用于精简规则的比赛；调整Shield.COST或DURATION可以迅速平衡护盾机制。维护者在不同活动场景下可以方便地调整这些参数而不需要深入代码修改。此外，前端入口文件 `public/config.js` 支持注入运行时变量，这意味着可以针对不同部署环境启用/禁用某些前端功能（虽然目前只用于配置后端URL，但完全可以扩展更多内容）。总体而言，**前端具备相当的配置灵活性**，满足比赛运营中快速变更需求。
    
-   **代码维护和升级**：前端采用主流的Vue框架，易于找到社区支持。组件划分清晰，逻辑与表现分离明显，为以后升级Vue版本或替换UI库打下基础。比如若将UI整体改为使用ElementUI等组件库，只需替换views/components层的实现，不影响底层GameManager等。TypeScript类型严格定义了接口和数据结构，如SseEventData、GameState等，让新开发者更易理解数据流向，也减少引入错误的风险。未来若增加新功能，建议遵循现有模式：UI交互 – 调用service接口 – 更新GameManager或相关管理器 – 通过事件通知UI，这样保持代码的一致性和可预测性。
    

综上所述，贪吃蛇平台前端在设计上留有充分余量，可以适应**更多地图和玩法**（通过模块增减和配置）、**更多用户和比赛**（通过水平扩展和赛事管理模块）、**更多算法类型**（通过策略扩展）等需求。维护者在进行二次开发时，应延续这种松耦合、高内聚的思想，善用事件总线和配置开关，以保持系统的高扩展性和易维护性。
